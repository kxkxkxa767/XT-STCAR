# 雷达优先绕桶：源码接入与原生验证（2026-09-28）

本轮基线为 `532f8fcf772edc70d6f49d2bf6177c47a4607c50`。用户提供的完整包
`XT-STCAR_lidar_first_sim_532f8fc (1).zip` 已读取并通过包内 66 项 SHA256 校验。
它是独立 Python 探针；本轮新增的是 Rust 生产模块通路及原生验证入口。
没有训练、改模型标签、部署车端、重启服务或发送电机命令。

## 已实现的通路

1. `robot-core/lidar_cones.rs` 从完整原始扫描聚类，处理零度接缝、缺束和距离突变。
   簇点数、尺寸、圆截面残差、弧深和可见凸面共同决定候选；长墙不切碎成桶。
   输入/候选/身份容量有界，超容量明确拒绝，不按最近两簇凑数。
2. `LocalWorld::update_lidar_cones` 使用已经校验的扫描、同采集时刻位姿和外参，独立建轨。
   默认至少 3 个不同扫描时间、确认间隔不超过 300 ms；长间隔重新确认。
   一簇多身份、多簇抢同一身份均阻断关联。未处理目标几何过期失效，已处理身份继续保留。
3. `ElementTrack.lidar` 保存 `source=lidar_geometry`、独立确认数及真实扫描时间。
   纯雷达目标 `observations=0 / last_visual_at=null / color=unknown`。
   不伪造视觉帧，也不受旧视觉 20 秒语义租期约束。几何有效期、误差漂移仍生效。
4. 同时刻 YOLO 地面投影经真实雷达唯一关联后可以补充原身份的视觉证据和颜色，
   不能创建另一个任务桶、覆盖雷达定位或单独延长其几何有效期。异步旧框缺匹配扫描时
   不伪称融合；本轮不加入扫描历史插值器。
5. 雷达模式第一桶允许任务轴前方至侧前方（超过原 ±45°），仍保留首桶任务轴左侧条件；
   第二桶依反向任务轴选择。候选数超过剩余桶数，或候选角度在误差及 7° 分离余量内
   无法区分时不分配。锁定 TrackId 后不每拍换最近桶；已处理空间排除继续生效。
6. 第一桶逆时针、第二桶顺时针，真实位移半圈、外侧经过、出口投影与姿态条件均保留。
   没有移植 Python Bézier 控制器，没有增大比赛容差、普通停车时限或搜索预算。

圆形截面是明确的模拟假设。半径默认 0.08–0.26 m，至少 5 点、最大 128 点，
弧深/残差与误差估计来自代码中的模拟配置，**尚无实车标定支持**。
方底座、遮挡分裂簇、真实扫描运动畸变、自遮挡和几何相同的柱体/腿仍未完成现场验收；
单平面雷达不能从完全相同的几何回波证明对象语义。不要将这些门写成通用物体分类器。

## 不再混用三个时钟

`RoadFrame` 新增两个可选字段，旧 JSON 仍能读取：

- `camera_captured_at`：真实相机采集线程提供的健康时间；未提供时沿用原语义帧时间。
- `observation_pose`：与 YOLO/元素帧同采集时刻的真实关联位姿。旧帧投影不能使用当前车姿。

扫描始终使用自己的同刻位姿。只有雷达模式的 `Cones` 阶段允许缺少新 YOLO 结果；
相机健康、雷达、姿态、心跳和执行有效期仍须新鲜。斑马线、灯和终点阶段照常校验语义年龄，
旧绿灯不能供后续阶段放行。已见灯前区域仍作为负约束保存、随年龄扩张误差，
不会因为绕桶阶段暂时没有新语义就消失。定位跳变超过原车辆速度/角速度与姿态误差界时停止。

这些字段已经贯穿同步控制、工作线程输入校验、命令最老源时间和最终执行证书。
只有输入适配器确实收到相机帧时才能填写 `camera_captured_at`；不能填循环时间冒充采集。
现有车端 vision-shadow 尚未接入自主控制，也没有因这次源码提交自动获得这个适配器。

## 元素顺序和异步旧路线

`OnlineMissionReport.task_revision` 在阶段或活动目标改变时递增；第一桶到第二桶虽然都属于
`Cones`，仍会改变 revision。任务完成账本和已处理几何排除不因目标重现或更换 TrackId 清零。

工作线程在处理出新 revision 后立即撤销旧任务 Drive，先发布新任务的 Stop，
下一输入再依实际采用的停车历史规划。这样既阻止晚到的上一桶路线重新采用，
也不会拿撤销前的执行历史证书授权新路线。原命令到期检查继续保留；没有无限等待。
单个 worker 的私有邮箱构成会话边界，新会话不能复用旧 worker 的计划。

## 配置与复现

新配置使用 `OnlineControlConfig::from_limits`（默认雷达优先），也可显式调用 `lidar_first`。
JSON 中通过 `online.world.lidar_cones` 给出检测配置。
历史缺少该字段的配置仍保持视觉优先；旧 `online_matrix` 显式使用
`visual_first_limits`，保留历史回归。所有自主配置仍要求 `simulation_only=true` 和
`measurement_status=unverified`，没有开放物理输出。

```bash
cargo test --workspace --locked --offline
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked --offline -- -D warnings

cargo run --release --locked --offline -p xt-stcar-robot-runner \
  --example lidar_matrix -- both all work/lidar-native
cargo run --release --locked --offline -p xt-stcar-robot-runner \
  --example lidar_matrix -- async-delay nominal_7x5 work/lidar-native-delay
```

原生矩阵逐场保存完整输入 JSON、有界状态日志 JSONL 和最后 128 次决策的完整源快照
（包括真实输入扫描、语义帧和各自时间/位姿，覆盖停车超时前后的窗口）。旧矩阵仍保留 16 条
小记录，日志字节上限未取消；状态日志不冒称完整每毫秒轨迹文件。
原导航、KnownFree、完整车体制动包络、
执行历史/证书、独立轨迹裁判全部参与。两桶视觉始终为空，只能从 raycast 原始扫描进检测器。
非桶语义与区域由 **仅在模拟器中的理想观测适配器** 提供，明确不验证 YOLO 或实景可见性。
原生连续矩阵使用无噪声扫描、理想位姿；另有完整包 8 帧带 2 mm 标准差噪声的扫描回归。
八场外形/桶位对应原型，灯前区域继续使用原工程规则配置，不能把结果当成逐行复刻 Python。

验证汇总与完整源文件哈希见 [机器记录](lidar-first-validation.json)。
