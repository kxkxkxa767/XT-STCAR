## 先测试，再安装

修复入口源码为 `scripts/vehicle-bluetooth-repair.py`，部署在车端独立目录：

```bash
sudo python3 /home/bianbu/xt-stcar-tests/20260916-bluetooth-repair/repair.py
```

当前SSH没有免密sudo，需要用户在自己的车端SSH终端输入密码。不会记录密码或调整sudo规则。

脚本核对板卡、rfkill身份、UART占用、现有控制器及三份文件SHA256，拒绝覆盖已有系统文件。随后复制到root拥有的临时目录，启动60秒上限的临时systemd服务；仅该服务的独立mount namespace将临时固件目录映射到标准固件路径，系统固件目录保持原样。执行的是与最终安装逐字节相同的初始化程序。

控制器出现后，上电并限时扫描10秒，要求实际报告Discovery started且接收到附近设备事件；单纯命令退出0不算通过。临时测试通过后停止测试服务、等待控制器释放，再安装：

- `/usr/local/bin/rtk_hciattach`
- `/lib/firmware/rtlbt/rtl8852bs_fw`
- `/lib/firmware/rtlbt/rtl8852bs_config`

安装后使用原已启用的 `realtek-bt.service` 再次启动、扫描并检查服务状态。最终失败会停止本次启动并移除本次新建的三份系统文件；临时阶段失败则不安装系统文件。成功后保持厂商蓝牙服务运行。不会替换厂商启动脚本、修改内核、操作底盘、配对任意设备或进行MCU刷写；蓝牙固件由标准初始化流程加载到模块运行内存。

扫描可以验证发现附近设备；配对、音频或其他具体协议仍需要用户指定设备后另测。如果附近没有可发现设备，验收会失败并跳过系统安装，不能因此直接断言硬件坏。

车端 `repair-result.json` 保存最后结果，`temporary-attach.log` 保存初始化日志。本机 `work/vehicle-bluetooth-repair/preparation.json`记录固定来源、编译与哈希。原故障证据见[蓝牙验证](vehicle-bluetooth-validation.json)。

## 第一轮失败与已完成修正

第一轮临时服务执行成功，但初始化日志报 `Can't set initial baud rate, 22, Invalid argument`，25秒内没有HCI，脚本退出且未写入三份系统文件。原始日志与报告保留为车端 `attempt1-{attach.log,result.json}`。

无设备访问的C探针证明：Zig自带termios头文件把B115200定义为数值115200，而车端GLIBC2.39头文件定义为编码4098；前者传给车端cfsetospeed/cfsetispeed均返回EINVAL。车端GCC探针两函数正常返回0。因此ELF架构和GLIBC符号版本检查通过，仍不足以证明头文件ABI兼容。

保持厂商C源码不变，从车端复制 `termios.h` 和 `bits/termios*.h`到独立头文件覆盖目录，以 `-I`优先于Zig自带头文件后重新交叉编译。修正版探针已在车端返回B115200=4098，两函数均成功，与车端GCC一致；修正版二进制SHA256为 `1a807e8408bd27212c7414b91072591c2168ddcd55cebf338f6afbbf150f65d8`。修复脚本已改为核对这个哈希。第一次使用-isystem仍被Zig内部搜索顺序覆盖，该中间尝试同样未用于系统安装。

此修正只覆盖独立蓝牙工具构建，没有修改全局Zig文件、系统glibc或Rust主工程；下一步仍须实际验证控制器、扫描与安装后的服务。

## 第二、三轮与启动时序修正

第二轮成功识别RTL8852BS，固件加载、HCI复位和Device setup complete均有真实日志，内核出现hci0；脚本随即调用bluetoothctl，却因BlueZ尚未发布控制器而提前退出，未安装系统。已新增限时等待bluetoothctl show实际报告控制器，再进行上电和扫描。

第三轮发生H5_SYNC重传超时，日志还提示receive packets in active state。上次初始化将控制器切到1500000波特率，关闭UART并不会恢复上电状态；临时启动路径缺少原厂脚本的蓝牙rfkill复位。已补齐同样的关闭1秒、开启1秒流程，并核对rfkill0的type/name只指向蓝牙。若等待被中断，finally恢复蓝牙电源。没有改变Wi-Fi rfkill状态。第二、三轮日志分别保留为车端attempt2/attempt3文件，均未安装系统。

修正版已经上传。模拟回归检查通过：BlueZ第一次未就绪时会等待下一次成功响应；复位等待被中断时仍写回开启状态。实际第四轮扫描与系统安装尚待用户sudo执行，不能把上述初始化成功写成扫描/连接成功。

## 第四轮：真实扫描通过，系统阶段遇到控制器切换

第四轮记录temporary_scan.scan_started=true、observed_device_count=8，说明临时环境已实际接收到附近8个设备的广播。随后安装同样三文件并启动厂商服务，系统阶段BlueZ曾就绪，但扫描未成功；脚本已移除新文件，system_files_rolled_back=true。

旧启动日志明确显示：17:25:23厂商初始化完成后，FIFO收到0并停止控制器，17:25:25又收到1，17:25:29重新初始化成功。第二次扫描撞上这次状态切换；具体哪个进程发送FIFO指令未确认，不归咎于特定桌面组件。控制器重启后尚未完成重扫，脚本17:25:33便结束回退。车辆之后被重启，当前启动日志与上轮需分开读取。

新脚本保留临时阶段的严格一次验证；系统阶段最多3次，每次重新等待BlueZ并要求Discovery started和实际设备事件，失败间隔3秒，同时保留stdout/stderr。没有降低验收条件或把旧缓存设备列表当成功扫描。模拟回归证明临时失联后可以重试、没有设备事件时仍拒绝通过。原始扫描输出只保留现场，不公开附近设备地址。

用户已明确授权自主继续，无需重复询问操作许可。但最新实际sudo -n仍返回a password is required，车端管理员认证尚未生效；不能以口头授权冒充已获得系统权限。车端修正版repair.py已就位，等待在用户自己的SSH终端执行此前sudo命令。修复范围不扩展到无人看护的底盘动作或MCU固件操作。


## 第五轮：定位并停用冲突的桌面插件

第五轮临时扫描实际收到9设备；厂商服务初始化后收到FIFO关闭指令，系统阶段三次验证均失败，三文件已回退。原始报告保留本机work目录，公开记录不含附近设备地址。

车端 `/usr/lib/python3/dist-packages/blueman/plugins/applet/KillSwitch.py` 的厂商分支在电源状态变更时同步调用 `realtek_bt.sh hci_start/hci_stop`。PowerManager初次同步未上电适配器状态时可能触发关闭；现场服务日志记录了初始化后的关闭，用户applet还被等待FIFO的hci_start子进程阻塞。这解释了临时服务正常、原厂服务阶段控制器消失的差异。

已在bianbu用户会话通过Gio.Settings将 `org.blueman.general plugin-list` 从空列表改为 `["!KillSwitch"]`，备份为 `~/xt-stcar-tests/20260916-bluetooth-repair/blueman-plugin-backup.json`。结束精确识别的阻塞用户子进程并重启用户Blueman applet后，D-Bus QueryPlugins成功返回，不含KillSwitch，PowerManager仍加载。只调整用户插件配置，没有改写系统Python模块或厂商服务。

如需恢复原插件配置，在bianbu桌面会话执行 `gsettings set org.blueman.general plugin-list '[]'`，再重启Blueman applet；这会重新启用原冲突路径，应先解决厂商插件逻辑。此次用户级修正已生效，但系统阶段仍需真实扫描复验。远程 `sudo -n true` 仍要求密码，现有授权不等于已完成sudo认证；执行上方同一安装命令后，以最终结果 `system_install_completed=true` 为准，中途“Installing”不算完成。
