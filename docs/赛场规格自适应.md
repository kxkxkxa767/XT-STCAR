# 赛场规格自适应

本模块把赛前测得的场地尺寸、区域边界和锥桶位置转换为任务布局，再生成可供 Rust 自主模拟使用的完整配置。
场地从 7×5 米换成其他尺寸时，不必逐个修改任务坐标，也不会按场地比例缩放车辆、白条或控制限值。

这一步需要提供测量值。目前没有无人扫描后自动识别全场边界、给锥桶分配赛道身份、定位灯前停车线和终点线的程序。
灯色识别不能给出灯的世界坐标或距离；`source: "measured"` 只记录数据来源，不能代替车辆标定。
当前生成配置仍为 `simulation_only: true`、`measurement_status: "unverified"`，本轮不连接车辆。

## 模块和数据流

| 位置 | 职责 |
|---|---|
| [`robot-core/src/field.rs`](../crates/robot-core/src/field.rs) | `FieldSpec` 保存米制测量；`FieldPlanning` 提供原车体、净空、网格分辨率和期望绕行半径；生成 `FieldLayout` 的区域、实际选用半径、通过点及切向朝向，检查尺寸与几何相容性 |
| [`runner/src/field.rs`](../crates/runner/src/field.rs) | `FieldScenario` 将场地规格与模拟斑马线位置、红灯持续时间组合，编译为 `SimulationConfig`；启动验证时检查派生几何与规格是否一致 |
| [`runner/src/main.rs`](../crates/runner/src/main.rs) | `field-example`、`field-layout`、`field-compile` 命令，严格读取 JSON，完成验证后原子写出 |
| [`config/field-example.json`](../config/field-example.json) | 一组明确标注为合成值的输入模板；不能作为现场测量记录 |
| [`robot-core/src/mission.rs`](../crates/robot-core/src/mission.rs) | 接收生成的搜索区、带可选到达朝向的通过点、灯前区域和终点，执行原比赛状态机 |
| [`robot-core/src/navigation.rs`](../crates/robot-core/src/navigation.rs) | 结合实时障碍、当前位姿及运动状态计算实际路线，继续执行完整车体、制动、运动和计算额度检查 |

流程是：**测量并填写规格 → 查看生成布局 → 编译并验证配置 → 启动控制器/worker → 根据传感器闭环运行**。
布局编译发生在启动前，不在控制 tick 中反复执行；运行中不通过改文件悄悄移动任务点。
若测量变更，应结束当前运行，重新编译、验证，再创建新的控制器。

## 坐标和测量方法

面向规则俯视图，局部原点设在场地左下角，`+x` 向右、`+y` 向上，所有长度单位为米，初始行驶方向为 `+x`。
场地边界、区域边界、锥桶中心必须使用同一坐标基准；若以挡板内沿建立可行驶边界，全部测量也应相对该内沿。
车端定位将来还需把实际世界坐标与这个局部坐标对齐，输入尺寸本身不能完成定位或相机标定。

以下范围依据工程内规则初稿的图 5；来源和仍需确认的规则事项见[规则与工程差距](赛项三规则与工程差距.md)。
表中的“未单列范围”表示初稿没有给该坐标独立区间，不表示允许任意填数：编译器仍检查它是否与场地和其他区域相容。

| `FieldSpec` 字段 | 怎么量、怎么填 | 初稿范围或含义 |
|---|---|---|
| `schema_version` | 填 `1` | 数据格式版本 |
| `source` | 合成试验填 `simulation`；现场测量填 `measured` | 来源标记，不启用硬件 |
| `length_m` | 左边界到右边界的水平距离 | 5–8 m |
| `width_m` | 下边界到上边界的垂直距离 | 4–6 m |
| `bottom_lane_width_m` | 下方人行道识别直道的横向宽度 | 1–2 m，单独测量 |
| `top_lane_width_m` | 上方灯识别直道的横向宽度 | 1–2 m，单独测量；可不同于下方 |
| `bottom_straight_span_m` | 左边界到下方识别区末端的水平跨度 | 3–6 m；不是从发车点算起的行驶距离 |
| `top_straight_span_m` | 上方识别区起点到右边界的水平跨度 | 3–6 m；区起点为 `length_m - top_straight_span_m` |
| `left_cone_from_left_m` | 左锥桶中心到左边界的水平距离 | 1–3 m |
| `right_cone_from_right_m` | 右锥桶中心到右边界的水平距离 | 1–3 m |
| `left_cone_from_top_m` | 左锥桶中心到上边界的垂直距离 | 2–3 m |
| `right_cone_from_bottom_m` | 右锥桶中心到下边界的垂直距离 | 初稿未单列独立范围，必须显式填写 |
| `crosswalk_search_start_m` | 下方人行道识别区起点的 x 坐标 | 初稿未单列独立范围；当前不得早于 0.8 m 发车区末端 |
| `light_front_x_m` | 上方灯前禁越线的 x 坐标 | 按实际灯前指定区域前沿测量；位于上方识别区且为终点区留出空间 |
| `light_stop_length_m` | 灯前指定停车区沿行驶方向的长度 | 按现场区域填写；初稿描述灯前 1 m 触发至灯之间区域，合成示例取 1 m |

锥桶测量用底座中心，不能把到锥桶边缘的净空直接填成中心距离。当前两中心由下式得到：

```text
右桶 = (length_m - right_cone_from_right_m, right_cone_from_bottom_m)
左桶 = (left_cone_from_left_m, width_m - left_cone_from_top_m)
```

尺寸各自在官方区间内，仍可能组合不相容。例如总长 5 m 却填 6 m 的直道跨度，或两个锥桶左右次序颠倒，都会拒绝编译。
编译器也检查识别区与锥桶底座相交、完整车体放不进固定区域、通过点越出净空边界和参考线段穿过底座等情形。
这些检查通过只证明已检查的几何条件成立，不证明车辆在给定转向、转向速率和时限内一定能跑完整场。

## 模拟场景参数与不缩放的尺寸

`FieldScenario` 的 `spec` 就是上表的 `FieldSpec`，外层还包括：

| 字段 | 用途 |
|---|---|
| `schema_version` | 外层格式版本，填 `1` |
| `cone_route_radius_m` | 工程期望的通过点半径，单位米；每桶实际值还受对应侧墙空间和扩张后的灯前禁带角点限制，输出见 `selected_cone_route_radii_m`。期望值和实际值均需满足当前最小转弯半径，不能作为跑完整场的保证或官方固定尺寸 |
| `crosswalk_near_x_m` | 合成相机绘制人行道时使用的实际前沿 x；必须让整个人行道落在搜索区内。任务接收整个搜索区，通过视觉决定停车点，不直接接收这个真值 |
| `light_red_duration_ms` | 合成灯的红灯持续时间，3000–10000 ms；任务仍依靠新鲜绿灯观察放行，不按这个计时器直接放行 |

发车区和终点区沿 x 方向各保持 **0.8 m**。人行道白条保持 **0.105×0.297 m**，条间距保持 **0.105 m**；
生成器按直道宽度容纳居中的奇数条白条，改变条数和横向跨度，不拉伸单条白纸。锥桶 **0.28 m** 方形底座按外接圆建模，
圆半径为 `0.14 × √2 m`，场地变大不会把锥桶也放大。

初始车体靠发车区前侧摆放，横向居中、朝向 `+x`；沿 x 的参考原点为
`0.8 - footprint.front_m - 2 × clearance_m`。车体仍需通过完整区域和原净空检查，
并非把参考原点固定在发车区中心，也没有缩小车体或安全距离。灯前及终点目标仍按完整车体在各自区域内居中生成。

车体前后悬、半宽、净空、速度、曲率及变化率、加减速、到达容差、斑马线停稳 3 秒和绿灯确认要求均沿用原控制配置。
不会为使较小场地通过而缩小车体、放宽碰撞检查或增加搜索额度；PP 仍为默认，LQR 仍为实验项。
较大官方拓扑的模拟总时长单独设置为 180 秒；原普通停车超过 10 秒判失败及源数据期限保持。

## 生成的任务顺序与感知边界

发车在左下方，沿下方直道寻找人行道并停车，然后按**右桶 → 左桶 → 上方入口 → 灯前停车区 → 右上方终点**的顺序运行。
每个桶的外侧半圆各布置 **5 个通过点，角度间隔 45°**：右桶从下方向右外侧再到上方，左桶从下方向左外侧再到上方，
最后加一个上方直道入口，共 11 个点。十个绕桶点都带该半圆的切向到达朝向，入口要求朝向 `0 rad`（`+x`）。
这些是带方向的任务要求，实际曲线仍由 Navigator 根据当前车辆状态和障碍计算，不是按时间播放固定轨迹。

每桶选用半径同时受期望值、侧墙空间及灯前禁带约束。计算所用的 `grid_resolution_m` 来自原导航配置，
不是新增的赛场测量值，也不会为适应场地而改变网格分辨率。具体为：

```text
车体外接圆半径 = hypot(max(footprint.front_m, footprint.rear_m), footprint.half_width_m)
grid_padding = 车体外接圆半径 + clearance_m + grid_resolution_m / sqrt(2)
扩张禁带角点 = (light_front_x_m - grid_padding,
               width_m - top_lane_width_m - grid_padding)

到禁带象限的距离 = hypot(max(角点 x - 桶中心 x, 0), max(角点 y - 桶中心 y, 0))
侧墙半径上限 = (该桶中心到对应侧墙的距离 + 锥桶外接圆半径) / 2
灯前半径上限 = 到禁带象限的距离 - clearance_m
selected_radius = min(cone_route_radius_m, 侧墙半径上限, 灯前半径上限)
```

禁带象限从该角点向右、向上延伸；从桶中心到象限的距离为整圆提供半径上限，因此约束覆盖整个参考半圆，
不会只检查五个离散通过点而漏掉点间弧线接近禁带角点的情况。额外减去的仍是原净空，用于保留参考附近的跟踪空间。
该规则在期望圆弧过于靠近侧墙或灯前禁带时收紧参考半径，只移动参考通过点，不缩小运行时的车体或禁带。
`FieldLayout.selected_cone_route_radii_m` 按 **右桶、左桶**顺序记录实际选值；实际半径小于原最小转弯半径时拒绝布局。
这是保守的几何生成规则，可能拒绝存在其他复杂绕法的场地组合；不会提高最大曲率去满足期望半径。
入口的 `x = max(length_m - top_straight_span_m, 左桶中心 x + 2 × cone_route_radius_m)`，
`y = width_m - top_lane_width_m / 2`，为转入上方直道预留纵向空间；这里使用期望半径，不能误写成两个桶各自选用的实际半径。
入口仍需位于灯前目标之前，并通过原布局几何检查，不会为了容纳入口而自动移动灯或终点。

任务新增可选 `cone_waypoint_headings_rad`，非空时与通过点一一对应；`Some` 朝向需为有限的 `[-π, π]` 弧度值。
任务同时满足原位置及朝向容差才推进，传给 Navigator 的当前目标朝向与该要求一致；
`PassThrough` 续段传递下一点的朝向，最后一个通过点的续段仍使用灯前朝向。
旧配置省略或使用空向量时保留仅按位置验收的行为，单项 `null` 表示该点不要求朝向；不会修改原容差。

带朝向的通过点还复用原定向必停目标的短连接保护：接近前方目标、处于原有界查询距离内时，
检查当前及候选下一周期是否还能接上经过完整认证的定向短连接，避免只看一段恒定曲率预览的评分而丢失最终对齐能力。
通过点仍按 `PassThrough` 执行，这项保护不把它改成必停点，也不会代替 Mission 根据真实观测验收。
无朝向通过点保留原分支；所有原碰撞、制动、时基、下一段要求及共享终端计算额度保持，单弧已有认证解时沿用原选择。

定向目标的原严格中心连接及适用搜索都未找到路径，且搜索以 `OpenEmpty` 或 `NodeBudget` 结束时，
新增 `arrival_region_after_search` 尝试一次有界的到达区域后备连接：先单段、失败后双段，仍只处理原连接器允许的前方近目标。
原严格 API 保留 `min(0.25 × goal_tolerance_m, 0.0001 m)` 的中心求解位置条件，原先成功的连接和搜索结果继续优先；
后备另以 `EndpointPolicy::ArrivalRegion` 判断数值收敛，不修改导航或比赛任务的配置容差。

后备必须满足：**实际积分终点的位置误差 + 累计位置误差界 < 原导航位置容差的一半**，
且**实际积分朝向误差 + 累计朝向误差界 ≤ 原导航朝向容差的一半**。
返回路径末点、终态朝向和曲率均来自同一段或两段真实模型积分结果，不会把末点替换成目标中心，
不会把模拟端点当作 Mission 已观测到的到达。两段之间继续传递实际末端曲率和累计误差，完整车体、原净空、
Grid/连续胶囊及有限灯禁带检查仍由原 primitive 通路执行。

后备与此前全部终端工作共用原 **256 次求解、1024 次迭代、65536 份预扣采样**总账，单个求解仍最多 8 次迭代。
它不分配新的 lattice 搜索节点；即使节点额度已耗尽，也只能使用剩余终端额度，原 `NodeBudget` 诊断继续保留。
终端总账耗尽、输入搜索状态不适用、几何或误差界未通过时仍失败；未给无朝向通过点添加这一后备。
连续恢复搜索中已经积分进入原到达区域的节点仍按自身验收条件处理，与这里后备连接采用的“半容差”条件分别记录。

`terminal_work.arrival_region_attempts` / `arrival_region_accepted` 记录该后备的调用与认证成功次数，阶段统计累计总数和单 tick 最大值，
零值省略以保持旧报告格式。这些计数不代表命令已经采用、车辆实际到达或比赛完成；没有新增逐 tick 落盘要求。

导航遇到膨胀 Grid 不连通时，不再据此直接断言实际车体通道不存在，而是在原剩余节点及终端额度内尝试已有的连续恢复搜索。
恢复仍检查完整车体、净空、边界、曲率弧长包络和累计积分误差；进入恢复时重新认证路径，不能给旧 Grid 缓存换个标签就继续采用。
旧 Grid 搜索成功的分支保持原行为，地图外目标仍按原规则拒绝；有恢复入口也不保证一定存在完整可认证路线。
输入模板和预先声明的 9 种场地参数保持，改变的是通用布局生成与规划处理。

当前适应能力的边界如下：

- 人行道可以在已配置的搜索区内改变纵向位置；识别到实际前沿后，Mission 根据同采集时刻的位姿生成停车点。
- 锥桶中心及绕行顺序来自赛前测量。运行时激光/视觉障碍参与避障和重规划，但局部避障不会自动改写整场拓扑或重新分配左右桶身份。
- 灯色来自图像，灯前停止区及禁越线来自测量；没有用灯色、图像框大小或模拟触发时刻推算灯的真实距离。
- 终点来自测量生成，沿用全车入区、朝向和停止判断；当前没有自动读取终点线标记并重新定位终点区的识别模块。
- 合成灯的可见范围和光电触发被限制在上方直道，车辆在下方直道经过同一 x 坐标时不会提前触发上方灯。这是模拟场景行为，不是车上接入了场地光电传感器。

## 有限灯前禁带

原 7×5 m 简化场景使用一条覆盖全场的灯前半平面。新官方拓扑会先从下方绕到右侧锥桶，
下方合法行程可能位于灯的 x 坐标之后，因此灯前约束需要限定横向范围。

新布局设置 `MissionConfig.light_boundary_region` 为上方直道区域。`HalfPlane` 保留原停止线，只把线后禁行范围限定在该区域的完整横向投影内；
斜向区域会采用四角投影得到的保守禁带。省略此可选字段时仍使用原全场半平面，旧配置语义和序列化保持兼容。

禁带的允许区域不是凸集，不能只判断矩形四角、胶囊两端各自是否在外面。
实现要求**同一个允许半空间容纳整个车体凸包或运动包络及其膨胀余量**，因此两端分居禁带两侧而中段穿入时会拒绝。
这一判据贯穿任务车体检查、导航停车圆、普通 Grid、连续恢复胶囊、采用前置检查和最终输出证书。
它可能保守拒绝部分贴近禁带角点的姿态；不会为通过角点而只检查车辆中心。
原停稳/绿灯条件、制动包络、采用时钟、lease 和计算额度保持。

## Mac 上使用命令

以下命令在工程根目录运行，使用本机 Rust；只读写普通文件，不打开车辆设备。先创建独立工作目录：

```bash
cd /Users/yuhaojin/Documents/XT-STCAR
mkdir -p work/field
cargo run --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- field-example > work/field/spec.json
```

编辑 `work/field/spec.json` 填写测量值，保持米制单位及左右/上下基准一致，再导出布局供检查：

```bash
cargo run --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- field-layout --config work/field/spec.json --output work/field/layout.json
```

`layout.json` 包含外围、发车区、搜索区、锥桶、实际选用半径、通过点及朝向、灯前区域和终点等派生结果；
它是布局结果，不是可直接交给 `autonomy-sim` 的完整配置。
确认布局后编译并运行离线闭环：

```bash
cargo run --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- field-compile --config work/field/spec.json --output work/field/compiled.json
cargo run --release --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- autonomy-sim --config work/field/compiled.json --output work/field/run.jsonl
```

`field-layout` 和 `field-compile` 省略 `--output` 时把 JSON 写到标准输出；带 `--output` 时验证及序列化全部完成后再原子替换文件，失败保留旧结果。
输入必须为普通文件且不超过 1 MiB；未知、重复、缺失参数及覆盖输入的同路径/符号链接会被拒绝。
派生配置保留原规格，启动验证会重新核对几何；不要单独修改其中某个终点、通过点或灯前区域来绕过规格。
三角函数生成的坐标经过 JSON 十进制写出、读回后可能相差 1 ULP，因此只对浮点叶允许
`8 × f64::EPSILON × max(1, |原值|, |读回值|)` 以内的舍入误差；对象字段、数组长度、整数和非数值内容仍严格一致。
这不改变车辆的米制控制容差，厘米级的独立路线改动仍会拒绝。

如需诊断，沿用 `autonomy-sim --trace` 的有界日志。默认仍为稀疏事件和结束写出，不增加每 tick 的场地配置落盘，
也不为减少 eMMC 写入而降低正常感知、控制频率。

## 验证范围与本轮结果

以前的 **8 组**来自同一个旧简化场地，组合两种输入延迟、两种采用延迟与 PP/LQR，是时序及运动回归基准。
该基准继续保留，不能把它描述成 8 种不同赛场的验证。

本轮另以 **9 种布局**检查不同外围尺寸、直道宽度、区段跨度和元素位置，关注真实 RGB/测距/位姿反馈进入状态机、
导航、采用检查及车辆模型后能否完成。它们与旧时序矩阵是两个维度；有限样本通过也不等于官方连续范围内的任意尺寸组合都能完成。
几何校验、同步整场、异步整场和目标板运行应分别记录，失败场也应保留原因。

最终固定输入为九种布局，每种分别运行同步/异步和 PP/LQR，共 **36 场，35 场通过**。
默认 **PP 18/18 通过**；实验性 **LQR 17/18**，`tall_5x6` 同步场在左桶阶段因普通停车超过 10 秒失败。
