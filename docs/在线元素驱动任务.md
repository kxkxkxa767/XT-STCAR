# 在线元素驱动任务

本轮新增 Rust 在线任务模式：任务顺序固定，元素位置和方向由每次传感器观测更新，再生成短距离目标交给现有规划与跟踪。这里的“在线”指处理连续传感器快照，不是联网。当前只接通内存 RGB、雷达、位姿和合成车辆反馈，**暂不接车，没有物理电机输出入口**。

截至 2026-09-16，冻结源码后的最终 19 场矩阵已运行：**正常场 0/15 完成，在线整场尚未通过验收**。4/19 符合预定检查，仅为缺标记、缺锥桶各同步/异步的安全停止。14 场独立裁判证明两桶，但随后都停在 ApproachLight 的停车区几何缺口；另有三个小场未通过第一桶，不能将所有失败归为灯信息不足。最终矩阵已有源码与实际运行凭证，565 项 Rust 工作区测试与双 RISC-V 链接已通过；本地包完整性不能替代比赛验收。正式证据使用 `online-mission-validation.json`、`online-mission-matrix.json` 和 `online-mission-experiments.json`。

最新 `legacy-integration` 旧八场 **8/8 完成且原性能门通过**；九项关键指标、序列化输出计数及八项单因素比较与 v9 精确一致。这不表示跨版本逐命令或完整轨迹逐点相等，也不能替代在线验收；上一轮场地适配 35/36 同样仅属于固定坐标模式的历史结果。

## 目标怎样产生

```text
同采集时刻 RGB / 雷达 / 位姿
        ↓
有几何信息的元素观测 → 雷达关联 → 有期限的元素轨迹
        ↓                         ＋ 局部空闲 / 障碍 / 未知
固定任务顺序、当前元素身份和动作进度
        ↓
搜索引导点 / 接近目标 / 绕桶短弧 / 区域内停车目标
        ↓
原导航、Pure Pursuit、运动预测、碰撞与制动检查
        ↓
Safety；异步再经原采用证书和最终 poll
        ↓
本拍模拟命令 → 新反馈 → 再估计、再规划
```

任务依次处理斑马线停车、两次规定方向的绕桶、灯前停车与绿灯确认、终点停稳。初始航向和任务顺序提供大致离开方向，不提供下一元素的精确位置。未看到下一元素时，搜索目标必须处于近期雷达支持的局部可通行空间；遇到未知空间、目标长期丢失或搜索预算耗尽，会停止或锁存故障。

绕桶目标由当前确认的桶中心、外形范围、车体净空和转弯能力生成。矩形车体沿圆弧切向行驶时，内侧边由实际半宽决定，半径下界为 `max(桶半径 + 车体半宽 + 净空 + 桶位置误差, 1/最大曲率)`。前后悬仍完整进入扫掠检查：分段端点的车体凸包，加各角点圆弧的最大弓高余量，覆盖整个运动过程；没有缩小车体。

入口对齐期间优先保持已经选中且仍可行的半径，必要时在安全下界内试较小候选，不因视点变化又跳回更大偏好半径。对齐完成或进入绕行后，若当前半径不再满足新的安全下界则停止。短弧随有效观测更新；绕行进度由实际输入位姿运动累积，单独移动桶估计不能制造“已经绕过”的进度。第二个桶不能跳过当前动作，已处理的桶保留独立排除记录，不能仅靠重新分配 ID 再做一次任务。

绕桶完成还要求实际离开出口中线：车辆沿出口方向相对桶中心的投影，至少越过桶位置误差。出口目标从圆弧顶端沿出口切线延伸 `桶位置误差 + 2 × 原目标位置容差`，并继续要求原位置、航向接近条件、外侧证据和规定半圈进度；圆弧进度仍最多累计到 π，不把延伸段虚算成转角。两份原位置容差让接近区域的最前沿仍有一份余量，不改变容差数值。曾出现仅差约 5–6 mm 未过中线，却因接近圆顶就提前计数的失败，专项回归明确拒绝中心前、恰在中线和中心误差内的提前完成。

短弧剩余转角为零时，仍按该绕行方向的切向姿态证明完整车体与净空处于 `KnownFree`；不会把零转角直接判为未知或自动放行。这个修正不改变上述真实出口投影、半圈与到达条件。

接近入口时若尚未处于所需切向，先由当前桶观测与规定绕行方向生成局部切向引导点，用原 `ArrivalBehavior::Stop` 的位置、航向和停稳条件完成对齐，再进入短弧；已经满足切向条件时不要求额外停车。该修正不增加定时 hold，不放宽原到达容差或搜索预算，引导段同样须通过已知空闲和制动检查。

有明确航向的稳定观测目标允许交给现有 Navigator 的距离为两个局部 horizon，默认 1.6 m，为侧向接近和切向对齐留出空间。超过该距离时，仍采用单个 horizon、默认 0.8 m 的无终端航向临时引导点；普通搜索也仍是单 horizon。不会给逐拍移动的临时点硬附终端航向。当前目标的完整车体和实际执行停车包络仍须通过原检查，这项策略的整场结果已记录在最终矩阵中，不表示正常场完成。

导航还针对真实采集的 26,580 ms worker 状态修复短连接：同一带方向目标的短缓存路线因车体相对参考漂移失效时，在粗栅格可能改成大回环之前，重新认证原严格短连接及原半容差到达区域。求解、积分采样和误差全部记入原共享预算，不重置额度；目标、方向、到达方式或边界变化时不能沿用该修复。该快照回归不等同于整场通过。

`Navigator` 初始化时固定 `TargetPolicy`：默认 `Fixed` 保留固定目标的搜索顺序，在线控制器统一使用 `RollingLocal`，不按场地或回放结果切换策略。49,580 ms 快照复现的无终端航向滚动点，在 `[0.35 m, min(2 × lookahead, 2 m))` 距离内先认证原账本中的单条前进圆弧；严格中心连接失败后，才尝试让真实积分端点及累计位置误差落在原半位置容差内。成功时保留实际端点，不吸附到目标，不增加航向要求，也不重置失败尝试的预算。

21,380 ms 的定向斑马线接近修正同样只用于 `RollingLocal`：原单/双弧后备均失败后，在原账本内增加一个目标曲率为零的短前进候选。当前执行曲率继续按原渐变模型积分到零，不直接拉直车头；长度来自目标在当前车体前向的正投影，目标距离小于 0.35 m。真实端点及累计位置/航向误差须进入原容差的一半，完整车体、边界与采用条件继续核验。初版通用点连接导致的性能退化保留在 `legacy-point-timing-final`；后续 `legacy-region` 和最新 `legacy-integration` 回归分别保留，旧八场恢复仍不代表在线整场通过。

距离小于 0.35 m 的定向 `RollingLocal` 目标，顺序为原严格双弧、原严格单弧、原到达区域证明，最后才进入 lattice 搜索；每一步继续使用同一账本，并对当前新边界重证。真实 18,100 / 18,800 ms 快照中短路线变成 3.70 / 7.22 m 回环的问题据此修正，三个邻帧原严格连接成功路径保持；`Fixed` 搜索顺序未改。

原到达区域及向零曲率前进候选都失败后，`RollingLocal` 可再尝试一个三段候选：短暂保持实际已应用曲率，按原曲率变化率回中，再直行。解析航向只用于选取段长，三段都由原 primitive 积分并连续传递曲率和累计误差；真实终点连同误差须进入原半位置/航向容差，总长和求解、迭代、采样仍受原共享预算限制。真实 38,400 / 38,500 ms 快照据此获得合法短接；38,300 ms 原成功和三帧 `Fixed` 结果保持，越线、障碍、误差、预算及非法输入负例仍拒绝。这是定向回归，尚非整场结论。

候选动作的连续性检查另有一条独立后备：仅在 `RollingLocal` 的原严格 continuation 候选全部失败后，从该候选完整控制周期的预测姿态、实际曲率及累计误差，用旧 `oriented_arrival_region` 在同一账本证明后续可达。这里不调用上述新增三段候选，也不直接报告任务到达或采用命令；候选原碰撞、制动与采用检查保留。

连续 recovery 的有限侧带边界可以追加整车扫掠证明，但世界矩形和每个障碍仍须通过原完整车体胶囊。对长度为 L、曲率绝对值不超过 K 的任意一段运动，端点车体凸包加 `L/2 × (1 + K × 车体外接半径)` 覆盖整段体积，再加原净空、重启余量、累计位置/航向误差及向外数值余量。整个包络必须处于同一个允许半空间，不能让各角分别从禁区两侧“绕过”检查；该证明只在 `RollingLocal + recovery + 有限边界` 启用，普通全局边界、`Fixed` 和没有姿态的参考点段仍保留原检查。

原胶囊和上述一阶界都拒绝时，还可依据该段实际运动模型做二阶时间域证明。设实际 `MotionTransition` 初始/目标的速度上界为 V、曲率绝对值上界为 K，原加减速度较大值为 A，原转向速率上界为 S，车体外接半径为 r，则每个车体点的二阶导数不超过 `M = A + V²K + r × (AK + V×S + V²K²)`。速度和曲率达到目标时状态连续，车体点的一阶导数也连续，所以跨饱和分段的完整运动仍落在两端车体凸包加 `M×dt²/8` 内。恒速或恒曲率段也保留原 A/S 上界，不新增经验系数。

dt 与实际积分一致：恒定规划速度的 primitive 使用同一次 `ds/max_speed`，rollout 则使用加减速模型解出的缩尾时长，与 `predict` 共享同一个 `duration.min(dt)`；不以可能接近零的测得速度反推时间。累计端点位置/朝向误差、原净空/重启余量、浮点外向余量和共同分离半空间继续保留，世界矩形与障碍仍用原完整胶囊。二阶界不增加采样或预算，仅作原证明失败后的第三份证明，`Fixed` 在计算它前即退出该分支。

真实 32,000 ms 输入夹具 `online32000_body_chord_tube.json` 及相邻四帧用于核对这条路径。新证明可能让原先被过粗边界拒绝的严格短接优先于半容差区域成功，因此后续轨迹可能改变；不声称所有旧成功帧命令不变。历史 32,100 ms 停舵状态即使找到短路线，仍会拒绝不能认证的执行候选。找到路线不等于允许 Drive；加减速、两种饱和顺序、减速到零、曲率穿零、真实角点越线、误差与非法输入均有专项回归，最终全场与构建结论另据正式报告。

仅 `RollingLocal` 在原停车可达圆盘证明失败时，可以再用完整 `StoppingEnvelope` 证明。它保留原两控制周期反应距离及全制动距离，速度取当前、候选与历史上界；以原最大曲率覆盖反应和制动期间任意正负转向变化，包含完整车体、净空、边界和障碍，不能假定沿某条名义弧刹停。实际制动力不低于配置仍是待车端标定的模型前提，原 rollout、误差、采用与最终来源门继续生效，`Fixed` 不走这条后备证明。

runner 的 `OrbitSpeedHint` 只给 `OrbitCone` 选速：使用实际来源姿态与根据当前观测短弧生成的五个参考姿态，以原最大曲率和感知年龄加控制周期的 horizon，检查各姿态完整停车包络的已知空闲。原速度上限已有证明时保持；否则最多八次二分，只返回真正已证的正下界，同时限制当前目标与 continuation 上限。无证明时不伪造零速目标，也不把真实较高速度改写为提示值。六个姿态只是选速提示，不是连续运动安全证书；实际来源、速度历史、负向边界、lease 和执行停车证明全部保留。

在进入导航前，绕桶阶段还会针对当前原始来源姿态的停车线负约束选速。存在 pending 或 confirmed 停车线且未获绿灯释放时，用原最大曲率、原 horizon 构造完整停车包络，同时检查当前 KnownFree 及所有停车线；线的误差仍从原观测/检查时钟增长。原速度上限通过则保持，否则最多八次二分寻找已证明的正速度上限，再同步限制当前目标和 continuation。该提示不修改停车线位置、时间、确认数、TTL 或任务阶段。

建议上限还必须实际可执行：以同源测量速度或同源规划投影速度，按原减速度与本拍实际间隔计算下界；间隔最多取原控制周期，并与有效 adoption 速度区间下界取较大者。投影的来源和计划时间必须匹配。若几何可证的正上限低于该下界，不把它向上夹成未经证明的值，也不下发当拍达不到的速度；提示缺席，由原独立执行门决定 Stop。真实来源、投影、已经采用的历史速度/曲率仍完整进入 `permits_command` 和异步证书，假设低速不替换真实较高速度。实际帧回归包含提前选速、pending/confirmed 同一误差时钟、continuation 同步限制、较短实际拍、错时钟、未知空间及采用下界冲突。

默认保留 Pure Pursuit。原速度、曲率、转向变化率、横向加速度、车体足迹、制动条件和任务等待条件继续生效。局部目标只是规划请求，不能直接授权 Drive；异步输出仍只能使用 `ControlPoll.command`，后台计划和诊断字段不能直接驱动车辆。新模式另外要求完整停车包络处于近期已知空闲空间，不是只检查目标点或包络的几个角点。

## 模拟真值与控制器输入

| 数据 | 谁可以使用 | 边界 |
| --- | --- | --- |
| `OnlineScenario.scene` 中的 `FieldScenario` / `FieldSpec` | 场景编译、RGB/雷达渲染、独立模拟裁判 | 用于摆放物体和判断碰撞、越界、最终完成，不用于在线目标生成 |
| `SimulationConfig.online_scene` | 模拟器 | 保存真实边界、灯前/终点区域与实验标记；控制器不接收该对象 |
| `SimulationConfig.autonomy` | 控制器 | `controller_config()` 从统一示例限值生成；改变场地或元素位置时逐值相同 |
| `pose`、`scan`、`road.observation`、`road.elements` | 在线任务与控制器 | 带采集时间、坐标系、质量和几何误差，不能伪造同步时间 |
| 局部轨迹与任务进度 | 在线任务 | 有界短期状态，不是全场精确地图 |

控制器配置保留兼容旧接口所需的部分字段；在线分支不读取旧任务的锥桶通过点、灯前/终点矩形来生成目标。`OnlineMissionConfig::from_limits` 只复制规则、车辆和时序限值。导航的固定宽范围运行边界是统一工程边界，不随真实墙壁位置改变；实际可行空间还须由雷达观测支持。

用于修改场景的 `online-example.json` 与可运行的 `online-sim.json` 不能混作纯控制器配置。`online-controller-sim.json` 仅用于已经准备好的强类型传感器快照回放。修改场地后需要重新编译模拟场景，但不为每个场地生成另一串在线必经坐标。

## 元素和局部空间接口

`ElementFrame` 保存 `captured_at`、`frame_id` 和最多 16 项 `ElementObservation`。时间为同一启动纪元的单调毫秒；位置与误差使用米，方向与方向误差使用弧度。观测在采集时刻的车体坐标系中表达，局部记忆根据同刻位姿转入里程计坐标系。

每项包含种类、颜色、位置、可选朝向、几何、来源、置信度、位置误差和朝向误差：

- 锥桶保留红/蓝颜色及地面投影候选。`associate_visual_cones` 检查同刻扫描、明确外参和唯一的连续雷达簇，关联成功才使用 `VisualLidar` 来源；不取图像方位附近任意一个雷达点冒充桶距。默认不假定“红色必定是第一只桶”，可选颜色身份必须显式配置。
- 斑马线由白纸条结构恢复近沿、宽深和穿越方向。先在米制地面坐标中估计几何，再用条带排列确定方向；不是把当前车头朝向写成测得的斑马线朝向。停车目标在车体前悬与原停车余量之外，再减去完整 `region_error`：位置误差加 `hypot(区域深度, 区域半宽) × 航向误差`，覆盖区域转动带来的边角位移。
- `LineRegion { lateral_half_width_m, depth_m }` 的位置是区域**近沿中点**，区域沿 `heading` 向前延伸 `depth_m`。`StopLine` 在此表示停车区域，区域远沿才是禁止跨越的界线。

`LocalWorld` 区分 `last_visual_at`（最后真实视觉确认）与 `last_geometry_at`（最后接受的视觉或雷达几何）；兼容字段 `last_seen` 等于后者。确认次数只随新的真实视觉帧增加，重复帧不会增加。

对已经视觉确认、有效且未处理的锥桶，当前 360° 雷达可在桶离开前向相机后维护同一身份，但必须匹配唯一连续点簇、原圆形半径、当前位姿及明确外参；分裂、短弧不确定性过大、多个身份争用同簇或矛盾时拒绝续期。雷达不能创建桶、猜颜色或增加视觉确认次数。

- `track_ttl_ms=1800` 是几何期限：没有新的有效几何，满 1.8 秒即失效。
- `cone_semantic_ttl_ms=20000` 是独立视觉语义期限：即使雷达每拍都更新，距离最后视觉确认满 20 秒仍失效。模拟默认值参考 0.85 m 半圈以 0.18 m/s 行驶约 14.84 秒，另留有限动作余量；较慢、较大或反复接近的轨迹必须重新观察，不能无限延长身份。

位置误差取最近视觉误差下限与本次独立圆簇拟合、量程及位姿误差中的较大值，包含短弧条件较差的影响；不会逐拍重复累加同一测量误差，也不会仅因激光精度较好就缩成 0.02 m。几何观测之间仍增加漂移，TTL 到期、矛盾或不确定性超限后不能作为有效目标。配置必须明确给出语义期限，旧文件缺字段时重新运行场景编译。

已处理的 `StopLine` / `FinishMarker` 仍可用真实同 ID 观测刷新几何，供整车离开边界时检查；`processed=true` 始终保留，不能被当作新任务重选。已处理的锥桶和斑马线保留冻结记录，矛盾失效的身份不能靠后续同色观测自行恢复。

区域身份还支持槽内真实重观察：有效且唯一匹配的旧 `StopLine` / `FinishMarker` 即使几何过期，也可接受新观测并保留 ID、`first_seen` 和 `processed`。跨过原 TTL 后首个新采集帧把 `observations` 重置为 1，默认第二个不同采集时刻的真实帧才恢复确认；该字段表示当前确认周期的独立视觉帧数。invalid 或歧义身份不能复活，未重见不会更新时间，锥桶确认规则不变。runner 显式 pin 当前引用的至多两个停车区/终点身份，避免其缓存槽被回收；pin 不延长 TTL、不恢复 invalid、不跳过两帧确认，也不让过期几何进入 `tracks`。未被保留且已回收的槽不能凭空找回旧 ID。

视觉/雷达的坐标往返可能产生约 1e-15 的纯浮点抖动（roundoff）。接受几何时，仅在 `32 × f64::EPSILON × max(1,|旧值|,|新值|)` 范围内保留上一浮点表示，位置最多 1 nm、方向最多 1e-9 rad；米级坐标的实际窗口约为 1e-14。这样避免等价目标反复清空导航缓存，不是测量滤波或毫米级死区。真实毫米变化仍更新，误差、观测时间和真实确认次数照常刷新。

局部空间明确分为 `KnownFree`、`Obstacle`、`Unknown`。无回波、缺束、过期扫描和近距盲区不会自动变为空地。当前采用相邻有限雷达束之间、截止到较近回波的三角区域模型；较远处的遮挡跳变不能否定近处已经支持的空闲部分，也不能把近回波后方填成空闲。

`LocalWorld` 对凸包和余量做整面积空闲证明，最多进行 64 次原空间查询：原外接圆能证明空闲时直接通过，否则用固定栈对定向外包矩形按长边自适应二分。每个接受叶矩形必须完整包含于其已证空闲圆；未通过的圆可继续细分，直到所有叶区域都有证明。两个子矩形共享同一浮点分界，内部、边缘和角点没有漏查缝隙，并保留向外数值余量。额度耗尽、无法继续细分或仍有未证明区域时拒绝。此前均匀覆盖仅保留作回归对照，生产实现已使用自适应证明。

负向 `Obstacle` 证据单独计算：最多 32 个输入点在固定容量内构成凸包，再检查同一有效扫描的真实有限回波到该凸包的欧氏距离，加入原量程、位姿、年龄漂移误差及余量。只落在外包矩形或覆盖圆额外区域内的回波，不会制造“请求凸包碰撞”的结论。既没有完整空闲证明、也没有距离支持的障碍证据时，结果为 `Unknown`。

绕桶半径候选使用三值结果筛选。已观测 `Obstacle` 拒绝候选，不能被其他 `Unknown` 单元掩盖；远处被桶遮挡的未来弧为 `Unknown` 时，可以保留为后续规划假设。**未来 Unknown 不代表可以执行：当前目标的完整车体和每拍实际执行的完整停车包络仍必须是 KnownFree。** 随后观测不支持该假设时重新规划或停止，不绕过执行门。

当前绕桶前方短弧尚非完整 `KnownFree` 时，目标提前采用原接近限速，默认 0.18 m/s；短弧完整已知空闲才允许原巡航上限 0.3 m/s。这样在遇到未知区域前就留出制动余量，实际命令仍须逐拍通过当前完整执行包络检查，降低限速不能代替空闲证明。

这仍是传感器插值模型，不能保证探测任意细小障碍。只有显式配置、位于该次扫描时刻的完整自车足迹能够覆盖自己的近距盲区，不能顺带填充车外未观测区域。

## 灯前与终点：仅有显式实验标记

官方规则初稿描述了灯前光电传感器到灯之间约 1 m 的停车区、80 cm 终点区及终点线，但目前取得的文字和厂商源码**没有确认现场停车线、终点线的具体可见图案**。灯色检测只给出红黄绿状态和置信度，灯的图像框不是地面距离。来源和未解决项见[赛项三规则与工程差距](赛项三规则与工程差距.md)。

因此 `GroundMarkerDetector` 使用独立实验协议：单条白色横条映射为停车区，双条映射为终点区，条长、厚度、间距、深度和锚点偏移都显式配置。两种条长必须可区分，避免双条遮掉一条时被误当成停车标记。图案裁剪、不完整或不匹配时不输出语义地标。

`bar_span_m` 是识别视觉编码用的条纹跨度，`region_width_m` 是协议明确声明的可用子区宽度，两者不能混作同一个测量值。默认灯前 0.6 m 条纹对应 0.8 m 宽子区，终点 0.9 m 条纹对应 0.9 m 宽子区；宽度来自显式协议，不读取模拟器的场地宽度。像素渲染、位置/方向误差和原车体尺寸保持；真实场地仍需确认是否存在这些标记及对应子区。

图案画在区域远沿附近，以便入区后仍可能观察到。检测器从 RGB 投影得到图案中心和横向轴，再按声明的区域深度及远沿锚点偏移还原近沿；不读取模拟器的区域坐标。穿越方向的 180° 双义用任务预期的车体方向消歧，不能通过该方向参数传入世界位置。标记尺寸和误差预算是模拟协议与工程先验，不是本车标定结果。

`ExperimentalMarkerConfig::default()` 为 `enabled=false`。`OnlineScenario::example()` 为演示协议显式写入 `experimental_markers_enabled=true`；这不代表真实赛场默认存在这些标记。关闭该开关或失去有效标记时，即使画面有绿灯，也不能产生灯前/终点几何来继续完成任务。短时等待和超时故障由任务及局部记忆处理；原停稳、绿灯新帧确认和全车离开灯区条件保持。

已取得的官方文字与图示没有给出可用于安全接近证明的“左桶出口到灯”距离正下界，不能按示意图比例补造距离。当前固定灯色 ROI 只识别颜色，无法定位地面停车区；在合成回放中，灯色会比地面标记更早进入视野。因此会出现“灯已见、区域几何尚不可见”的信息缺口，任务不能借灯色继续向前猜距离，可能安全 Stop 后超时。

另一个独立缺口是已确认地面标记在清尾前退出前向 ROI。特定默认直行条件下，StopLine 最后完整可见约在车体参考点距远沿 −0.26 m，整车清尾至少到远沿 +0.18 m；余下 0.44 m 以原接近速度 0.18 m/s 行驶，忽略误差也约需 2.44 s，超过 1.8 s 几何期限。按当前像素、位姿及漂移项估算约为 4.89 s。**这两个数字只针对所述默认直行条件，不是所有轨迹或场地的不可行证明，也不是实跑成绩。** 默认终点双白条在居中停点附近也仅有约 0.03 m 的最近边可见余量，须检查实际 RGB 与最后有效帧。

已 processed 的线持续可见时会刷新；真正看不见后不会伪造 fresh，也不增加过期线的正向任务获取、绿灯确认或清尾授权。过期 StopLine 的负向约束继续按原来源时钟增加位置和航向误差，完整包络仍可被证明位于保守线前，或完全位于扩大后的有限侧带之外；不会在 TTL 到期瞬间把整条带全封死。需要正向地标证据的任务仍受原有限重观察与停止条件约束。后续可评估保持地标可见的局部轨迹，或在明确协议下、确有可见条边且锚点唯一时跟踪部分标记；这些尚不是已完成能力，也不能保证所有场地可行。

终点完成还显式要求已按原判据证明全车清空灯区。即使合法确认的终点与停车区重叠，到达并停稳却尚未清尾仍进入 Fault，不能先标记终点已处理；部分重叠但确实完成清尾的情形可以继续。不同标记名称不能替代空间顺序和整车边界证据。

真实接入前还需确认实际可见标记及其位置关系；若没有标记或不存在持续观察路径，需要新的定位测量或可验证的局部先验。问题不只是等待接车测一遍。当前不宣称能够在现场识别停车区和终点，**也不能保证在线整场完成**。

## Mac 使用

以下在工程根目录运行，依赖已缓存时可使用 `--offline`。这些命令只生成配置或执行合成模拟，不需要模型、ONNX Runtime、相机或车辆。

```bash
cd /Users/yuhaojin/Documents/XT-STCAR
mkdir -p work/online
cargo run --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- \
  online-example > work/online/scenario.json
cargo run --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- \
  online-compile --config work/online/scenario.json --output work/online/compiled.json
cargo run --release --locked --offline -p xt-stcar-robot-runner --bin xt-stcar-robot -- \
  autonomy-sim --config work/online/compiled.json --output work/online/run.jsonl
```

创建模板前选一个新文件名，避免 shell 重定向覆盖已有配置。修改 `scenario.json` 的 `scene` 可移动场地或元素；`occlusions` 的 `from_ms`、`through_ms`、`cones`、`markers` 用于声明有限时间内的视觉遮挡。雷达仍根据自己的场景生成，视觉遮挡并不等于删除物体。`online-compile` 完整解析、校验和序列化后才写输出，非法输入不覆盖已有输出。

交付配置的对应关系：

| 文件 | 用途 |
| --- | --- |
| `config/online-example.json` | 在线模拟场景模板：模拟器真值与实验标记开关 |
| `config/online-sim.json` | 已编译的完整模拟配置，交给 `autonomy-sim` |
| `config/online-controller-sim.json` | 统一在线控制器配置，交给 `autonomy-replay`；需要带 `road.elements` 的同步快照 |

矩阵工具按预先声明的场景运行同步或异步 PP，并保留失败。先查看场景，再运行指定项：

```bash
cargo run --release --locked --offline -p xt-stcar-robot-runner --example online_matrix -- cases
cargo run --release --locked --offline -p xt-stcar-robot-runner --example online_matrix -- sync nominal
cargo run --release --locked --offline -p xt-stcar-robot-runner --example online_matrix -- async-trace nominal > work/online/nominal-async-trace.json
cargo run --release --locked --offline -p xt-stcar-robot-runner --example online_matrix -- both all > work/online/matrix.json
```

模式为 `cases|sync|async|async-trace|both`，第二参数为场景名或 `all`；时序扰动项仅运行异步。工具输出实际摘要及逐项 `passed`，存在非预期失败时非零退出。预期缺失标记/锥桶场景应安全未完成，不能把“没有完成”一概算成通过，也不能省略故障与终态检查。普通 `autonomy-sim` 默认只向 stdout 输出摘要，`--output` 保存必要事件/终态；`--trace` 才增加有界细节。

同步摘要的 `recent_online_attempts` 最多保存末 16 项观测/任务诊断（通常间隔至少 100 ms，终态可提前插入）；异步 `recent_attempts` 最多保存末 16 次已发布尝试，包括被拒绝或故障的报告。`active_track` 可保留最后接受的几何供排查，出现该字段不代表身份当前仍有效。

只有显式 `async-trace` 才输出 `offline_plan_trace`，最多保留前 2048 个不同计划时刻，超出部分计入 `omitted_trace_plans`。这些是有界模拟诊断，不加入真实控制快照，也不能把观察到的后台计划当作实际执行命令。

模拟摘要还提供独立 `online_referee`：它只用场景中的真实锥桶与车辆实际积分轨迹，检查规定左右侧、进入/通过顺序、实际有符号半圈进度、入出航向和车体碰撞。控制器的 `processed_cones` 不能代替裁判证据；检查 `order_valid`、`trajectory_valid`、`both_completed` 与 `failure_reason`，再结合停车、绿灯、终点和实际终态判断。裁判真值不回传给控制器，这仍是模拟验收，不是实车证明。

库接入使用常驻 `RoadPipeline::new_online(road, vision, markers)`；`vision=None` 走 RGB 几何与显式灯 ROI，传入模型配置则复用原生 ORT Session。`process` 用车体前方消歧，`process_with_heading` 可传入明确的预期车体方向。旧 `RoadPipeline::new` 保持 `elements=None`。这是内存接口，尚未提供自动打开真实相机并驱动底盘的 CLI。

## 验证边界与当前记录

针对初始斑马线问题，场景编译增加联合检查：最早搜索区近沿不得小于完整初始车体前沿加原 0.15 m 停车余量。检查不依赖渲染器把斑马线实际摆在哪里；精确边界接受、下一浮点值拒绝，未放宽原容差或控制参数。

已有局部回归覆盖标记旋转/尺寸/遮挡/禁用、斑马线几何朝向、锥桶颜色、RGB 流水线、元素发布容量和初始停车边界。它们证明相应输入条件下的接口行为，不证明整场成功、真实识别率或目标板实时性。
