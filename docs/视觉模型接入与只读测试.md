# 视觉模型接入与只读测试

2026-09-21，依据用户提供的[视觉接入建议](https://chatgpt.com/share/6ab1253d-6b94-83ee-802d-3144198924cc)，对当前视觉入口作了修改。
本次完成模型接口和只读处理链，没有训练真实赛道模型，没有给车辆发送行驶指令，也没有部署或重启车端服务。

## 已实现的处理链

驾驶台唯一相机采集线程 → JPEG 与采集完成时间 → 一个在处理、一个待处理的最新帧 → 独立 `vision-shadow` 进程 → 常驻 Rust ORT Session → 类别映射 → RGB 几何 → `RoadFrame.elements` 与诊断网页。
Python 只负责相机、限长 IPC、预览和保存；模型推理、解码、地面几何仍在 Rust。`vision-shadow` 不打开串口、相机或电机接口，不产生底盘命令。既有 `PerceptionWorker` 和在线控制器仍可复用同一 `RoadPipeline`；此网页入口本身不启动 `OnlineSession` 或自主导航。

- 默认继续使用官方 80 类配置 `config/yolo26n.json`，兼容既有模型与 provenance。
- 自训练示例 `config/yolo26-race4.json` 明确列出 `cone_red / cone_blue / traffic_light / crosswalk`。`class_names` 的顺序必须与 ONNX 相同；`road_classes` 按名称绑定角色，类别号不再写死在识别器里。旧 COCO 的灯类别 9 只保留在明确的兼容映射中。
- 锥桶检测框只是候选：还要找到同色完整 RGB 连通区域、满足锥形条件并观察到底部，才作地面投影。颜色冲突、底部被框裁掉、空框都不会凭框生成有效锥桶。置信度结合模型分数；米制误差沿用投影像素误差与独立误差下限，不使用 `1-score` 冒充米。
- 斑马线仍从框内实际完整白条组计算前沿、方向和区域尺寸，空框不能生成距离。红绿灯在对应 ROI 内用 HSV 判断，保留暗灯、过曝、冲突和 Unknown。未声明的模型类别不用于灯、桶或斑马线候选；未配置候选角色的经典 RGB 分支保持原行为。
- 输出来源为 `GroundProjection`，**不标成 `VisualLidar`**。以后须由真实同时刻雷达关联成功后使用原有融合入口。此处没有伪造雷达或位姿同步。
- StopLine / FinishMarker 继续使用显式实验标记协议；只读入口默认禁用。没有凭训练类别或灯的位置虚构停车区。

`RoadDetector` 目前仍只接受 `simulation_only=true / calibration_status=unverified`。可以观察真实相机中的检测框，但示例 H 矩阵的米制元素仅作诊断。真实地面标定、误差界与导航准入没有在本次被宣称完成。

## 自训练权重的导出

模型环境保持 `.venv-model` 与 Ultralytics 8.4.142 等原锁定版本；不更换架构、导出布局或量化方式。
训练由队友负责，本轮不启动训练。需先收集本车视角的真实数据，按上述四类标注，并按采集场次拆分训练与验证数据。官方 COCO 权重不能直接识别这些自定义类别。停车线/终点外观尚未确定，暂不加入训练类。

队友交付 `best.pt`、有序类别表、数据集版本/训练验证划分、训练参数与验证指标；类别顺序为 `0 cone_red / 1 cone_blue / 2 traffic_light / 3 crosswalk`，如改变顺序必须同步修改模型配置。

在该锁定环境完成 YOLO26n Detect 训练、得到可信的 `best.pt` 后，为自己的权重建立训练来源清单。下面命令只生成清单，不训练模型、不下载权重；把路径与数据集版本改为真实值：

```bash
.venv-model/bin/python - <<'PY'
import hashlib, json
from pathlib import Path
weights = Path('models/race4-best.pt')
spec = json.loads(Path('config/yolo26-race4.json').read_text())
record = {'schema_version': 1, 'model_family': 'yolo26n',
          'weights_sha256': hashlib.sha256(weights.read_bytes()).hexdigest(),
          'dataset_version': '替换为实际数据集版本及划分标识',
          'class_names': spec['class_names']}
Path('models/race4-training.json').write_text(json.dumps(record, ensure_ascii=False, indent=2)+'\n')
PY
.venv-model/bin/python scripts/export_yolo26.py \
  --weights models/race4-best.pt --spec config/yolo26-race4.json \
  --trusted-training-manifest models/race4-training.json
```

`--trusted-training-manifest` 表示明确信任自己提供的 PyTorch 权重；SHA 相同不等于陌生 pickle 安全。未给这个参数时仍只允许原官方权重的已知 SHA。
脚本在加载权重前核对清单、权重 SHA 和类别表，加载后核对 nano 架构元数据、Detect 与 one-to-one 分支。
导出保持 FP32、静态 `images [1,3,320,320] → output0 [1,300,6]`、opset17、batch1、nms=False、quantize32。
provenance 同时保存训练来源、数据集版本、权重/ONNX SHA、类别表、导出参数和库版本；Rust 启动时再绑定这些记录、模型哈希及 Session 的实际接口/metadata。
这些记录便于审计，并非数字签名或真实数据精度证明。自训练 `.pt/.onnx`、数据集和生成 provenance 不提交 Git。

## 单图与连续诊断

单图会返回检测框、阶段耗时、`RoadObservation` 和 `ElementFrame`：

```bash
target/release/xt-stcar-robot road-detect \
  --config config/road-perception-sim.json --image /path/to/frame.jpg \
  --model models/race4-best.onnx --vision-config config/yolo26-race4.json \
  --runtime-lib /path/to/verified/libonnxruntime.so
```

Mac 请改用工程内已验证的 `toolchains/onnxruntime-macos-arm64-1.29.0/lib/libonnxruntime.1.29.0.dylib`。
`vision-shadow ROAD_CONFIG MODEL ORT_LIB MODEL_SPEC` 的 stdin 每帧为一行 JSON 头加准确长度的 JPEG：
`{"sequence":1,"captured_at_ms":1234,"jpeg_bytes":12345}\n` 后跟 JPEG 字节，后面直接接下一帧头。
源码序号和毫秒时间必须严格递增；帧头 ≤4096 字节，JPEG ≤2 MiB，解码 ≤1920×1080、分配预算32 MiB。
stdout 先给 ready，再逐帧给 JSON；输出中的时间沿用相机拥有者 `cap.read()` 返回后的主机单调时钟，不在推理结束时重打时间戳。它不是曝光硬件时间，也未去除 UVC 缓冲延迟。

网页进程将超出的待处理帧替换掉，记录丢弃数。进程初始化最多40秒、单帧 IPC最多5秒；超时或失败锁存诊断错误并退出独立感知进程，不自动反复拉起。控制线程不等待该进程，不修改原看门狗和锁定条件；CPU负载对实车遥控的影响仍需现场测试。

## 在车端驾驶台启用

默认关闭，需要将新版网页文件（包括 `vision_shadow.py`）、RISC-V `vision-shadow`、配对模型/provenance 和配置部署到自己的目录。不能使用 Mac 可执行文件或 dylib。
当前代码没有自动替换车端文件；下面是部署后的配置步骤：

1. 复制 `config/vision-shadow.example.json` 到车端 `~/xt-stcar-console/vision.json`。
2. 填写五个实际存在的绝对文件路径，核对 ORT 库和模型，再把 `enabled` 改为 `true`。官方基线用 `yolo26n.json`；自训练权重用对应的 race4 配置。
3. 更新 `run-service.py` / `start-console.py` 为本工程脚本，再在车辆锁定、没有人操控时重启 `xt-stcar-console.service`。后续服务启动会读取该配置。

也可显式启动已有驾驶台命令并追加：

```text
--vision-shadow /path/to/vision-shadow /path/to/road.json /path/to/model.onnx /path/to/libonnxruntime.so /path/to/model-spec.json
```

相机仍只有驾驶台打开一次；不再额外运行另一个采集程序。配置示例故意保留 ORT 路径占位并默认关闭，避免误认为已在车端完成部署。
网页新增“视觉模型 · 只读诊断”，显示同一源帧的检测框、灯色、元素、帧龄及耗时；过期结果变暗。保存按钮保存**服务器最新完成的检测帧**为单张 JPG，文件名包含帧号，可在原下载区重新下载。点击时可能比页面上次刷新更新一两帧，不承诺冻结当前显示帧。

## 验证与性能范围

见 [验证记录](vision-integration-validation.json)、[官方模型连续推理](vision-shadow-official-validation.json)、[RISC-V ELF](vision-shadow-riscv-elf.json)。
常驻会话跳过前5帧预热，统计最近120个结果的工作线程中位数/P95/最大耗时，另列 JPEG解码、预处理、ORT运行、检测解码、几何处理和发布帧龄。
原生 intra-op 线程仍固定2；工作线程耗时还包含 IPC 和绘制。主机数字不代表车端帧率，未启用量化或厂商 EP。

复现纯文件测试与测量：

```bash
cargo build -p xt-stcar-robot-runner --bins --locked --offline
.venv-model/bin/python -m pytest -q tests/test_yolo26_tools.py tests/test_vision_shadow.py
cargo build -p xt-stcar-robot-runner --bin vision-shadow --release --locked --offline
.venv-model/bin/python tests/measure_vision_shadow.py \
  --image /path/to/bus.jpg --output work/vision-shadow-measurement.json
```

Mac 测试中的四类 ONNX 是**合成常量输出夹具**，用于验证接口、颜色几何和失败路径，不是训练结果。真实官方模型的15帧样例仍检出5个目标；赛道四类精度、逆光/远距离效果、实车性能、相机标定及多传感器融合仍待实测。
